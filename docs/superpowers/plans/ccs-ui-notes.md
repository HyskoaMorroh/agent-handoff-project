### 核实 3：「最后活动」失真 —— 成立，且是大面积真 bug

`core/vitals.py:1452` 取的是 `datetime.fromtimestamp(st.st_mtime)`，即**文件 mtime**，而不是转录内最后一条记录的 `timestamp`。

全盘实测（63 个含时间戳的会话，比较文件 mtime 与文件内最后一条 `timestamp`）：

- **22 个**会话偏差 > 60 秒
- **10 个**偏差 > 1 小时
- **3 个**偏差 > 24 小时
- 最大偏差 **241243 秒 ≈ 2.8 天**（`C--Users-devin` 下 `f64bc79e…`）

截图取证的两例：

| 会话 | 文件内最后 timestamp | 文件 mtime | 偏差 |
| --- | --- | --- | --- |
| `1ee778a2…` | `2026-08-25T10:32:21.504Z`（本地 18:32:21） | `2026-08-25T10:41:26.231Z` | 545 秒 |
| `6640504f…` | `2026-08-24T23:34:39.422Z`（本地 8-25 07:34:39） | `2026-08-25T11:28:58.510Z` | **约 11 小时** |

第二例正是截图上「最后活动 2026-08-25 18:41:26」的来源问题：该会话真实最后活动在 8-25 早上 07:34，界面却显示当晚。mtime 会被任何后续触碰推后（sidechain 追加、工具写回、同步软件、备份程序），因此它不是"最后活动"的可靠代表。

影响面不止显示：mtime 同时是排序键（`vitals.py:1751`、`1755`、`cli.py:569`）、分组代表值（`cli.py:502`）、以及"最差会话推荐"的输入（`core/handoff.py:444` 的 `picked.sort(key=lambda v: v["mtime"])`）。一个 2.8 天的偏差足以把真正该交接的会话排到后面。

### 核实 4：两张卡片显示同一秒 —— 非代码缺陷

GUI 侧 `gui/static/app.js:394` 用的是 `ago(r.mtime)` 与 `title: r.mtime_text`，两者都取自各自的行对象，不存在共享状态或对象复用。两卡显示同一秒的解释：截图拍摄于 19:10–19:11（见文件名时间戳），当时卡2 的文件 mtime 尚未被推进到 19:28，与卡1 的 19:41 之间恰好读到相近值；该文件在截图之后又被写入过。属 mtime 本身不稳定的次生现象，根因仍是核实 3。

### 修正后的缺陷清单（按严重度）

1. **「最后活动」口径错**（真 bug，影响 63 个会话中的 22 个）：用文件 mtime 代替转录内最后一条记录时间，最大失真 2.8 天，且污染排序与"最差会话"推荐。
2. **归属口径只反映进程 cwd**（设计口径问题，非数据错乱）：用户在 kirara 目录里启动会话讨论 agent-handoff-project，工具如实报告 cwd = kirara。「涉及仓库」其实已探测到多个候选（图 1 的"另有 1 个"），但代表值固定取 cwd，把真正的工作对象折叠隐藏。下游「用这个仓库交接 / 复制工作目录 / 复制续接命令」沿用该代表值，是用户体感"复制进去就改错代码"的直接来源。
3. **输出目录漂移**（真 bug）：`find_plan` 判定过宽（README 也能当计划文档），导致交接产物落在仓库根而非 `docs/`。
4. **试运行不显示输出路径**（可用性缺陷）：`app.js:887` 仅在 `!lastDry` 时才渲染 `gui.handoff.wrote`，试运行时用户看不到将写往哪里，无法在写之前发现第 3 条。

### 核实 5：真正的目标仓库确实被采集到了，只是被藏起来

在沙箱里按 `core/vitals.py:838-842` 的算法（前 260 行、`iter_path_candidates` + `nearest_repo` 验证）重放截图卡片 1 的转录 `1ee778a2…`，得到 `repos[]` 顺序：

```
[0] e:\output\kirara-ai\kirara-ai3.3.0b8          ← 卡片显示这个
[1] C:\Users\devin\agent-handoff-project          ← 用户真正在改的，被折叠
[2] E:\output\kirara-ai\kirara-ai3.3.0b8          ← 同 [0]，仅盘符大小写不同
```

三点结论：

1. **`C:\Users\devin\agent-handoff-project` 就在列表里**，位置 `[1]`。界面那句"（另有 1 个）"里藏着的正是用户要找的仓库。信息**已经被采集到**，缺的只是排序与展示。
2. **`repos[]` 存在大小写重复**：`[0]` 与 `[2]` 是同一个目录，只因转录里出现过 `e:` 与 `E:` 两种写法。`nearest_repo`（`platform.py:306-315`）用 `Path.resolve()`，Windows 上不统一盘符大小写，于是同一仓库占了两个槽位。这也是"另有 1 个"计数偏小的原因——去重后本该是"另有 1 个"，未去重则把重复项也算进候选池，挤占真实候选的可见位。
3. **排序依据是"在转录里第一次出现的位置"**，不是"哪个更可能是工作对象"。cwd 所在的仓库天然出现得最早（第 3 行就有 `cwd`），所以它永远排第一，真实工作对象永远靠后。

这条把"归属口径"从一个见解升级为可验证的缺陷：不是"工具口径与用户期待不同"，而是**工具手里握着正确答案却按一个与相关性无关的键排序**。

### 核实 6：存在一个比 cwd 与"提到过"都强得多的证据源 —— 写工具的 `file_path`

`repos[]` 收集的是"正文里提到的路径"（`vitals.py:838-842`），这是弱证据：粘一次日志就能污染。但转录里还有一类**从未被利用**的强证据：`Edit` / `Write` / `MultiEdit` / `NotebookEdit` 这些工具调用的 `input.file_path`。那不是"提到"，是**这个会话真的改了这个文件**。

对截图两例逐一统计（沙箱内解析全部 tool_use 块）：

| 会话 | cwd | 写工具目标仓库 | 读工具目标仓库 |
| --- | --- | --- | --- |
| `1ee778a2…` | `e:\output\kirara-ai\kirara-ai3.3.0b8` | `c:\users\devin\agent-handoff-project` ×**258** | 同一仓库 ×99 |
| `6640504f…` | `e:\output\kirara-ai\kirara-ai3.3.0b8` | 无（357 次工具调用，0 次文件写） | 无 |

第一例是决定性的：**258 次文件写入，全部落在 `agent-handoff-project`，一次都没落在 cwd 所在的 kirara 目录。** 卡片上"用这个仓库交接"指向的那个仓库，这个会话从头到尾没改过一个字节。

扩大到全盘 12 个有写工具证据的会话：

- **cwd 推出的仓库与"写得最多的仓库"一致的只有 1 / 12。**
- 8 个会话 `cwd` 字段本身缺失（前 400 行预算内没读到），此时 cwd 路径完全不可用，而写工具证据仍然明确（如 `fc0e9aac` 有 242 次写入指向 `agent-handoff-project`，`cce7cbc7` 有 114 次指向 `anyrouter-check-in`）。
- 三个 cwd 为 kirara 的会话（`1ee778a2`、`7f410e02`、`809adf54`），写目标全部是 `agent-handoff-project`（258 / 281 / 4 次）。

这条把方案方向定了下来：**证据分层**。可靠性从高到低是

1. 写工具 `file_path` 的仓库（改了什么 —— 最强）
2. 读工具 `file_path` 的仓库（看了什么）
3. `cwd` + `nearest_repo`（在哪启动 —— 现状唯一依据）
4. 正文提到的路径（提过什么 —— 现状的兜底，最弱）

第二例同时给出了必须处理的边界：**没有任何文件工具证据的会话**（纯讨论、纯搜索、被中断在早期）。这类会话只能退回 cwd，界面必须说明"依据是启动目录，本次会话未改动任何文件"，而不是假装同样确定。

### 核实 7：`repos[]` 大小写重复的量化

前述 `[0]` / `[2]` 重复不是孤例。`platform.py:306-315` 的 `nearest_repo` 用 `Path.resolve()`，Windows 上不规范化盘符大小写；而 `platform.py:222-224` 的 `norm_path` 会小写化，却**不用于 `repos[]` 去重**。同一目录出现 `e:` 与 `E:` 两种写法即占两槽。这直接压缩了"另有 N 个"里真实候选的可见配额。

### 核实 8：Codex 侧的归属错得比 Claude 侧更彻底

Codex 的 `cwd` 语义与 Claude 完全不同。实测 316 份 rollout：

- **151 份**含 `exec_command` 的 `workdir` 参数（每次命令执行的真实目录，是强证据）。
- 其中 `cwd` 推出的仓库与"命令执行最多的仓库"一致的只有 **16 / 151**；**135 份不一致**。

不一致的原因不是排序问题，而是 Codex 的 `cwd` 根本不指向代码：

```
cwd      : C:\Users\devin\Documents\Codex\2026-08-17\1-e-output-kirara-…
cwd->repo: (not a repo)            ← 该目录不含 .git，nearest_repo 返回空
workdir  : e:\output\kirara-ai\kirara-ai3.3.0a5  (551 calls)
```

Codex 把 `cwd` 设成自己的**会话工作区沙箱目录**（`~\Documents\Codex\<日期>\<名字>`），那不是用户的仓库。于是 `SessionRow.repo`（`vitals.py:540-544`）的 `nearest_repo(cwd)` 返回空，直接落到 `repos[0]` 兜底 —— 也就是最弱的"正文提到过"证据。**Codex 会话的归属判定实际上从来没有用上强证据。**

同时发现两个此前未被利用的权威字段（均在 `turn_context` 记录里，逐轮记录）：

- **`workspace_roots`**：数组，Codex 明确声明的工作区根列表。实测样本里含 1–3 个条目，包含真实仓库路径。这是**上游 harness 自己给出的"这个会话在哪些根上工作"**，比任何推断都可靠。
- **`turn_context.cwd`**：逐轮的当前目录，会随会话推进变化。项目A 现状只读第一个 `session_meta` 的 `cwd`（`vitals.py:798-809` 的 `_seen_meta` 守卫），因此拿到的是**会话开始时**的值，而非最后状态。

Codex 侧的证据分层因此与 Claude 侧不同：

1. `turn_context.workspace_roots`（harness 声明 —— 最强）
2. `exec_command` 的 `workdir`（命令实际在哪跑）
3. `apply_patch` 的目标路径（改了什么；实测该样本仅 2 次，比 Claude 的 `Edit` 稀疏得多）
4. 最新一条 `turn_context.cwd`
5. `session_meta.cwd`（现状唯一依据，且常指向沙箱目录而非仓库）

另外确认 Codex 的记录信封与九种 type 与既有认知一致，实测样本分布：`event_msg` 1806、`response_item` 1921、`world_state` 41、`turn_context` 54、`compacted` 32、`session_meta` **2**（不是 1 —— 印证"只取第一个 meta"会漏掉后续状态）。

### 核实 9：Codex 的 mtime 比 Claude 的更不可用

324 份 rollout：

- **287 份**文件 mtime **早于**文件内最后一条记录时间（负漂移），中位 −222 秒，p10 −1815 秒，最差 **−15228 秒 ≈ 4.2 小时**。
- **268 / 324** 份文件的 mtime 与**文件名里的会话开始时间**相差不到 2 秒。

也就是说 Codex 的 mtime 实际上记录的是**会话创建时刻**，与"最后活动"无关。项目A 用 `datetime.fromtimestamp(st.st_mtime)`（`vitals.py:1452`）在 Codex 侧等于把"最后活动"显示成"最早活动"。

排序影响的全盘量化（492 个会话，Claude + Codex 合计）：

- 按 mtime 排序与按真实最后活动排序，**只有 122 / 492 个会话位次相同**。
- 最大位次偏移 **93 位**。
- Top-10 重叠 9/10（最近的几个会话恰好还在，但整张表的中后段完全乱了）。

### 核实 10：修正"最后活动"的技术可行性已验证

不需要全量解析。实测 63 份 Claude 转录：

| 只读文件末尾 | 能找到 `timestamp` 的比例 |
| --- | --- |
| 8 KB | 57 / 63 |
| **32 KB** | **63 / 63** |
| 128 KB | 63 / 63 |

Codex 侧同样在 32–40 KB 尾读内稳定命中（信封字段 `{"timestamp":…,"type":…,"payload":…}`，实测尾部 17 行里 16 行带信封级 timestamp）。

一个必须处理的边界：全盘单行最大长度 **3458382 字节 ≈ 3.4 MB**。尾读窗口内可能只有一行残行且不完整，所以解析必须容忍首行截断（丢弃第一个不完整行），并在窗口内一个都没找到时回落到更大窗口或 mtime，且**标注回落原因**。
